Capacity

Each phase has a fixed number of agent seats, set per repository. A task waits on the backlog, or at the entrance of a phase, until a seat is free. Spare seats are visible; a phase that is always full is the bottleneck, and adding a seat is a configuration change.

Timeouts

An agent may hold a task for a bounded time per phase. When the timeout passes, the factory stops the thread and the task fails that phase with a technical reason: timed out. The clock never pauses. A Build thread that sits four minutes in a rate-limit wait and then times out has timed out; a system failure is also a failure.

Which kind it was is read off afterwards: a thread that stopped giving reasons is the harness's problem, a thread that kept working and ran over is the agent's.

Two kinds of failure reason

The one who attaches the reason is who noticed.

  • Technical, attached by the factory: timed out, the quality gate failed, the pull request is missing, an artifact is malformed, merge conflict, deploy failed.
  • Functional, attached by the agent: the request is contradictory, the plan cannot be done inside its constraints, the review's findings.

A rising share of technical failures means the harness, the timeouts or the gate are wrong; a rising share of functional failures means the intake or the prompts are.

Retries

A retry is a full re-run, with the past attached. A failed task goes through every phase again, Intake first, so the plan is made again with the failure in view. Each new thread is prompted with the failure reasons and the ids of the failed attempts' threads, and threads can read each other.

Those threads are not deleted: a human can open one and leave feedback in it, and the next attempt reads it. The branch and its commits stay too, so Build continues from the previous work.

Strikes

A task can absorb five.

Failed atStrikesMeaning
Intake5final at once; if the agent whose job is to understand the request cannot, retrying is noise
Build, the quality gate1handed off without a passing gate; cheap, and the report says exactly what to fix
Build, timeout or cannot be done2two are survivable, a third is not
Review, including a merge conflict1findings are cheap to act on, so several rounds are allowed
Release1a technical failure in the automation before the merge

Strikes add up: two build failures and one round of findings is five, and the task is done. The weights say what the factory believes: a plan that cannot be made is not worth a second try, code that fails twice is probably the wrong approach, and a failed gate or a review finding is what the loop is for.
