# Plan for #6, attempt 2

## Goal

Add the page `site/review.html`, titled "Review", describing the Review agent and its verdict, and link it from the nav on `site/index.html` as "Review". One pull request, no split.

Attempt 1 built this correctly but failed Review's pre-check: the branch did not merge cleanly into `master`, because `site/index.html` changed on `master` (the Release and The loop nav links were added) after the branch was cut. This attempt must start by bringing the branch up to date with `master`, then redo the nav edit on top of it.

## Scope

- First step: `git fetch origin && git merge origin/master` on this branch (a normal merge, no rebase, no force-push). Resolve the conflict in `site/index.html` by taking `master`'s version and then adding the Review link; keep every nav link `master` already has. The merge brings in `master`'s other files (`site/loop.html`, `site/release.html`, `site/style.css` changes, `factory/` files); those are not unrequested.
- `site/review.html`: a complete page with `<!DOCTYPE html>`, `<html lang="en">`, `<meta charset="utf-8">`, `<title>Review</title>`, `<link rel="stylesheet" href="style.css">`, a `<main>` wrapper, an `<h1>Review</h1>` and a nav matching the one on `site/index.html` after the edit (Home, Release, The loop, Review). Reuse the file from attempt 1 (`git show d2303ec:site/review.html`) and only update its nav. These are what a valid page needs to pass `npm test` and match the existing pages; they are planned, not unrequested.
- Page content, in this order, all taken from the issue text:
  1. Review has 2 seats and a 5 minute timeout. Its artifact is `factory/reviews/N-A.md` on the task's branch, with a link on the pull request.
  2. Input: the task's worktree with a passing `factory/gates/N-A.md`, the plan in `factory/plans/N-A.md`, the pull request and the diff; the reviewer is told not to open the builder's thread; before the agent starts, the factory checks that the branch merges cleanly into `main`, and a conflict is a Review failure without a model call.
  3. The review shape in a `<pre>` block, exactly the template in the issue (`# Review of #N, attempt A` through `READY | FINDINGS`), HTML-escaped where needed.
  4. "Verifiable because": the end of Review is a command; the review file exists, every criterion from the plan appears in its Criteria section with a diff reference or a reason, and the last line is one of two words; `READY` with any unchecked criterion, violated constraint or defect is refused as malformed.
  5. "On failure": `FINDINGS` is a functional failure reason and costs one strike; the task goes to the back of the Backlog and is re-processed from Intake, with the review file and a link to this thread as part of what every following agent reads.
  6. An `<h2>` "The agent that writes is not the agent that judges": the builder sees its own plan and output and grades them kindly; the gate is a tool the builder runs but does not write; the reviewer sees only the plan, the gate report and the diff, cannot ask the builder anything, and treats a missing proof as a finding, not an oversight.
  7. The prompt, verbatim from the issue ("You review a pull request produced by an unattended factory. ... Do not comment on style the quality gate already enforces."), in a `<blockquote>`.
- `site/index.html`: add exactly one line, `<li><a href="review.html">Review</a></li>`, at the end of the existing nav list (after The loop). Nothing else on the page changes relative to `master`.
- No inline `<style>` and no `style=` attributes; styling comes only from the shared stylesheet.
