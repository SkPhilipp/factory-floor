# Plan for #28, attempt 1

## Goal

Add the producer of `site/state.json`: a Node script that reads the factory's GitHub issues, `factory:*` and `strike:*` labels, bb threads and gate/review reports, and writes `site/state.json` in the contract #17 landed on `master` (`phases` of `{id,title,seats,timeout_s,agent}`, `items` of `{number,title,phase,status,strikes,thread_url,issue_url,started_at,defect}`, consumed by `buildModel` in `site/floor.js`). #17 is closed and merged, so this is unblocked. It fits one pull request: one script, one test file, one fixture and a README section; no split.

Design, so the build does not guess:

- `scripts/floor-state.mjs` exports a pure `buildState(inputs)` and has a CLI. `inputs` is `{ now, issues, threads, reports, phases? }`:
  - `issues`: `[{ number, title, state, url, labels: [name], comments: [{ body, createdAt }] }]`.
  - `threads`: `{ "<thread id>": "<bb status>" }`.
  - `reports`: `[{ issue, attempt, kind: "gate"|"review", ok, text }]`, where `text` is the first failing line.
  - `phases`: optional; default is the five phases of `site/state.json` on `master` (backlog 0 seats/0 s/no agent, intake 1/600/agent, build 2/1800/agent, review 1/900/agent, release 1/0/no agent).
- Item rules in `buildState`:
  - Only issues carrying the label `factory` or any `factory:*` label become items; other issues are ignored. Items are sorted by `number` ascending.
  - Phase comes from the label: `factory:intake|build|review|release` give that phase, plain `factory` gives `backlog`, and `factory:done` gives `release` with status `merged`. Merged items stay in `items` so the tally comes from counts.
  - `factory:failed` gives status `failed`; its phase is the phase named in the newest comment matching `^(Intake|Build|Review|Release) started, attempt (\d+)`, or `backlog` if there is none.
  - `strikes` is `N` from the `strike:N` label, `0` without one.
  - `status` is `running` when the thread id from the newest `... started, attempt N: thread \`thr_x\` URL` comment has bb status `running`, else `waiting` (`merged` and `failed` as above). Only for `running` are `thread_url` (that URL) and `started_at` (that comment's `createdAt`) set; otherwise both are `null`. `issue_url` is the issue's `url`.
  - `defect`: of the item's reports take the highest `attempt`, a review beating a gate of the same attempt. If that report has `ok: false`, `defect` is its `text`; otherwise `null`. So a defect is set when a gate or review fails, survives while the next attempt has no report, and is cleared only by a later attempt's passing report. Merged items have `defect: null`.
- CLI: `node scripts/floor-state.mjs [--input file.json] [--out path]`. Without `--input` it gathers inputs with `gh issue list` / `gh api` (issues, comments), `bb thread show --json` for each thread id found in comments, and the gate and review files under `factory/gates/` and `factory/reviews/` on `origin/master` and on remote branches named `bb/N-*` or `factory/N` (gate `Result: **PASS**|**FAIL**`, review `READY`|`FINDINGS`). It reads phases from `bb factory repos list --json` when that parses and gives seats and timeouts, else uses the defaults. `--out` defaults to `site/state.json`. The file is written whole via a temp file and rename, and only when the content differs from what is there.
- Publication decision, documented in `README.md` under a new `## State file` heading: the script only writes the file. The factory loop runs it after every state change; when `site/state.json` changed it commits the file through the same pull-request path as every other change (branch `floor/state`, merged by Release), so the base is never pushed to directly and the published site updates when that merge deploys.

## Scope

- `scripts/floor-state.mjs`: new, as above.
- `test/floor-state.test.mjs`: new tests of `buildState`, plus one CLI test with `--input` and `--out`.
- `test/fixtures/floor-inputs.json`: new fixture with `now` `2026-01-01T00:10:00Z` and these issues:
  - `#21` labels `[factory]`, open;
  - `#11` `[factory, factory:intake]`, comment `Intake started, attempt 1: thread \`thr_a\` http://localhost/threads/thr_a` created `2026-01-01T00:05:00Z`, thread `thr_a` `running`;
  - `#12` `[factory, factory:build, strike:2]`, one gate report attempt 2 `ok: false` text `Gate failed: missing test`;
  - `#14` `[factory, factory:failed, strike:5]`, comment `Review started, attempt 3: thread \`thr_b\` http://localhost/threads/thr_b`, thread `thr_b` `idle`;
  - `#10` closed `[factory, factory:done]`;
  - `#15` `[factory, factory:review]`, gate attempt 1 `ok: false` text `old` and gate attempt 2 `ok: true`;
  - `#99` `[bug]`, which must not appear.
- `README.md`: keep the existing text; add only the `## State file` section.
- Kept valid by convention, not unrequested: `package.json` needs no edit, because `scripts.test` (`node check.mjs && node --test test/*.test.mjs`) already runs new test files; `scripts/` holds `.mjs` so no `package.json` `type` change.
- Not in scope: `site/floor.js`, `site/floor.html`, `site/style.css`, `check.mjs`, and the sample `site/state.json` (it is regenerated by the loop, not by this change).

## Constraints

- May touch only `scripts/floor-state.mjs`, `test/floor-state.test.mjs`, `test/fixtures/floor-inputs.json` and `README.md`. Files under `factory/` do not count.
- Must not change `check.mjs`, `package.json`, anything under `site/`, or the existing text of `README.md`.
- No dependencies, lockfile or build step; Node built-ins only, and `gh`/`bb`/`git` called through `child_process` only in the CLI gathering path, never in `buildState`.
- Budget: at most 4 files changed and 350 added lines outside `factory/`.

## Acceptance criteria

- [ ] `scripts/floor-state.mjs` exports `buildState` as a pure function (no `child_process`, `fs` or network use inside it) returning `{ phases, items }` with exactly the keys of the #17 contract.
- [ ] Running `buildState` on `test/fixtures/floor-inputs.json` yields items `10, 11, 12, 14, 15, 21` in that order, with `#99` absent.
- [ ] `#21` is `backlog`/`waiting`; `#11` is `intake`/`running` with `thread_url` `http://localhost/threads/thr_a` and `started_at` `2026-01-01T00:05:00Z`; `#12` is `build`/`waiting` with `strikes` 2; `#14` is `review`/`failed` with `strikes` 5 and `thread_url` `null`; `#10` is `release`/`merged`.
- [ ] `#12` has `defect` `Gate failed: missing test`; `#15` has `defect` `null` because its attempt 2 gate passed; a test shows a defect stays set when a later attempt has no report yet and is cleared only when a later attempt's report has `ok: true`.
- [ ] A test shows merged items remain in `items` and that `tally` from `site/floor.js` on the output gives `{ merged: 1, failed: 1, retried: 2 }`.
- [ ] A test feeds the output to `buildModel` from `site/floor.js` without throwing, and shows an item with more running threads than seats still appears exactly once.
- [ ] Tests cover the input variants the fixture does not: zero items, an item with no `strike:` label, two `strike:` labels (the highest wins), two `started` comments (the newest wins), a thread status that is not `running`, and a `factory:failed` item with no `started` comment (`backlog`).
- [ ] The CLI with `--input` and `--out` writes valid JSON, leaves the output file's mtime unchanged when run twice on the same input, and does not touch `site/state.json` when `--out` is given.
- [ ] `README.md` has a `## State file` section stating that the loop runs the script after every state change and publishes a changed file through a pull request, never a direct push to the base; its first four original lines are unchanged.
- [ ] Only the four listed files differ from `origin/master` outside `factory/`, within the budget.
